# Design decisions

**Status:** DRAFT. Add a row whenever a decision is made or changed.

## Decisions

| # | Date | Decision | Reason |
|---|---|---|---|
| D1 | 2026-10-10 | Breaks count as slots for spacing. | One break between two performances satisfies "at least one break". |
| D2 | 2026-10-10 | No separate "guest performance" concept; guests are breaks. | Simpler model; guests have no conflicts. |
| D3 | 2026-10-10 | Plan for a simple UI for non-technical organisers. | Core logic stays separate from any UI so it can be added later. |
| D4 | 2026-10-10 | Finder enumerates schedules systematically (not randomly). *(Amended by D30.)* | Shows every option when options are sparse; when plentiful, organiser pins more items. |
| D5 | 2026-10-10 | Output format is CSV. | Simple; other formats may come later. |
| D6 | 2026-10-10 | Organiser can fix positions of performances and breaks. | Supports chosen opening/closing acts; user can remove constraints if none are feasible. |
| D7 | 2026-10-10 | Tools named "schedule checker" and "schedule finder". | Clearer than Tool 1 / Tool 2. |
| D8 | 2026-10-10 | Shared core modules, thin tools on top. | Checker and finder must agree on what "valid" means. |
| D9 | 2026-10-12 | Number of breaks is a parameter; pinned breaks count towards it. (Q1) | Simple and predictable. |
| D10 | 2026-10-12 | Fixed positions are numbered from 1. (Q4) | Organisers count from 1. |
| D11 | 2026-10-12 | Breaks are interchangeable when enumerating. (Q5) | Schedules differing only by which break is which are the same schedule. |
| D12 | 2026-10-12 | Multiple schedules are written to **one CSV file, side by side**: a `position` column and one column per schedule. (Q3) | Easier for the organiser to compare options. Supersedes the earlier "one file each" proposal. |
| D13 | 2026-10-12 | The checker reads the same side-by-side format, so a file with one schedule column is the single-schedule case. | Finder output can be fed directly to the checker. |
| D14 | 2026-10-12 | No automatic "find the largest k". After a successful run the tool shows a short prompt inviting the user to try a larger k in a later run. (Q6) | Keeps the finder simple; the organiser stays in control. Supersedes the earlier proposal. |
| D15 | 2026-10-12 | The finder has an optional shuffle: a **seed** number that reorders the order in which items are tried. Same seed gives the same list; with no seed the fixed default order is used. (Q8) *(Amended by D31.)* | Early schedules in a fixed order look alike; shuffling starts the list somewhere different while staying complete and repeatable. |
| D16 | 2026-10-12 | The "try a larger gap" prompt after a successful run is a plain invitation with no feasibility check. (Q7) | Keeps the finder simple. |
| D17 | 2026-10-12 | The finder lets the user choose which schedules to output from its numbered list using one option, `--pick`: a single number, a range (`6-10`), a comma-separated list mixing both (`1,4,9` or `1-3,7,20-22`), or `all`. After each run the tool prints the exact command for the next batch. (Q9) *(Confirmed by D33.)* | Covers connected batches and unconnected choices with one rule; organisers who are not comfortable with the command line do not have to work it out. Replaces the earlier `--start`/`--count` idea. |
| D18 | 2026-10-12 | When a seed is used, it is printed on screen and added to the output file name (e.g. `schedules_seed42.csv`). (Q10) *(File name amended by D43.)* | The result can be reproduced. |
| D19 | 2026-10-12 | A limit caps how many schedules one run writes (default 100, confirmed 2026-10-12; changeable with `--limit`). With `all`, the first `limit` schedules are written and the tool says whether more exist. An explicit pick longer than the limit is refused with a message, not silently shortened. *(Confirmed by D33.)* | Avoids enormous tables; never hides that results were cut off. |
| D20 | 2026-10-12 | Schedules are numbered by their place in the finder's list (with the same seed, the same input always gives the same numbering). Output columns keep those numbers (`schedule_1`, `schedule_4`, `schedule_9`). *(Amended by D32.)* | A picked schedule can be found again later. |
| D21 | 2026-10-13 | Suspected typos in names are reported as warnings only. The tool never changes names because they look alike; the organiser corrects the source file. | Keeps one source of truth: the data file itself. |
| D22 | 2026-10-15 | The schedule reader checks the file (columns, position numbers) but not the contents. Unknown, missing or repeated performances are loaded as written and reported by the schedule checker. | The checker's job is to say exactly what is wrong with a proposed order; a reader that refused such files would stop it. |
| D23 | 2026-10-15 | The checker records one violation per pair of neighbouring performances of a performer (not one per performer, and not every pair). | Easy to scan, and checking neighbours is enough. |
| D24 | 2026-10-15 | If a schedule has structural problems (missing, unknown or repeated performances), the spacing check is skipped for it. | Spacing is meaningless without a sound arrangement. |
| D25 | 2026-10-15 | An unknown performance name in a schedule gets a "Did you mean..." hint when a real name is very close (similarity 0.85). Nothing is changed automatically. | Helps organisers fix the file themselves, consistent with D21. |
| D26 | 2026-10-15 | Result wording lives in `report.py` (shared layer), not in `cli.py`. | The command line and the UI must show identical wording and cannot import from each other. |
| D27 | 2026-10-15 | The command is `schedule-checker`. Exit codes: 0 all valid, 1 any invalid, 2 input or command problem. | A script can tell "invalid" from "could not check". |
| D28 | 2026-10-15 | With more than 10 schedules, valid ones appear only in the overview table. | Keeps long runs readable. |
| D29 | 2026-10-17 | The finder's search engine is **OR-Tools CP-SAT**. The custom backtracking engine is not built. Brute force stays in the tests as the independent check. (Q2) | Notebook experiment: both engines matched brute force on the tiny shows, but on the real show CP-SAT answered all 6 cases in about 0.1 s each (including proving that k=3 with 2 breaks is impossible) while backtracking gave up on 3 of the 6. Backtracking was also found to miss valid schedules at k of 2 or more (see `search-approaches.md`, section 5). |
| D30 | 2026-10-17 | "Systematic" (D4) now means: **complete** (every valid schedule is eventually listed, none twice) and **repeatable** (same input, seed, OR-Tools version and one solver thread give the same list). The order is the solver's, not dictionary order. | Dictionary order was a property of backtracking only. Pinning more items remains the way to get more varied options. |
| D31 | 2026-10-17 | The shuffle seed (D15) is kept, still printed and added to the file name (D18). It changes where the list starts; **how** is decided by a small test when `solver.py` is built (Q14, settled by D38). Without a seed the default list is used. | The seed can no longer reorder a search we wrote ourselves; whether the solver's own seed has the effect must be checked, not assumed. |
| D32 | 2026-10-17 | Schedule numbers (D20) are stable for the same input, seed and OR-Tools version. The tool prints the OR-Tools version on screen, and the exact version in use is recorded in `environment.md`. Numbers saved in an output file never change, so nothing already saved is lost. | The solver's order is not guaranteed across versions. Only same-machine repeatability has been tested. |
| D33 | 2026-10-17 | `--pick` and `--limit` (D17, D19) behave exactly as written. Under the hood, "show more" re-runs the solver from the start and discards the schedules before the first one chosen; there is no bookmark. To say whether more exist beyond the limit, a run asks for one extra schedule. | Cheap enough: 100 schedules from the real show took 0.12 s, 1,000 from a synthetic 20-performance show 0.89 s. |
| D34 | 2026-10-17 | When no schedule exists, the finder runs the plain-language pre-checks first. If pins are involved, it then reports a set of pins that cannot all hold together, taken from the solver (each pin is switched on as an assumption). This replaces the earlier "retry with each pin removed in turn". The set is enough to explain the failure but not necessarily the smallest, and other such sets may exist. | One solve instead of one per pin. Worked correctly in the one case tried in the notebook. |
| D35 | 2026-10-17 | `ortools` goes in a new optional group `finder` in `pyproject.toml`, and also in `dev` so tests and the notebook work. The `solver-experiments` group is removed. It is not a core dependency. | Keeps the schedule checker installable without the solver, as `environment.md` intends. |
| D36 | 2026-10-17 | The fixed-positions reader checks the **file**, not the contents (as D22). It refuses: no `position` column, no usable item column, a position that is not a whole number from 1, a missing item, a position used twice, a performance pinned twice. All problems are reported together with row numbers. Unknown names, positions beyond the show, too many pinned breaks and pins that clash too closely are left to the finder's pre-checks. A file with no pinned rows is allowed, with a warning. The item column is called `item`; with exactly two columns the one that is not `position` is used whatever its name. | The finder's job is to explain exactly what is wrong, and a reader that refused such files would stop it. A position or performance used twice can never be a usable pin, so it is refused at once, like a repeated position in a schedule file. |
| D37 | 2026-10-17 | The text of a schedule file (`format_schedules`) is built in `io.py` next to its reader (`parse_schedules`), not in `report.py`. Names come from the performer file. The text reads back with `parse_schedules`, so finder output can go straight to the checker. | A file format belongs with its reader. `report.py` is for wording meant for people. |
| D38 | 2026-10-17 | The shuffle seed works by changing the order in which the model is built: performances and clashing pairs are sorted by a SHA-256 hash of the seed and their names. With no seed they are alphabetical (the default list). The solver's own random seed is fixed at 1, and one thread is used. (Q14) | Tested on 2026-10-17. The solver's own `random_seed` gave the same first 5 schedules for seeds 0 to 3 on the 20-performance show, so it does not move the start of the list. Shuffling the build order gave 4 different lists from 4 settings, each repeatable, and the same 152 schedules on the tiny show. A hash is used instead of Python's `random.shuffle` because that may change between Python versions; the list was identical in separate processes with different hash randomisation. |
| D39 | 2026-10-17 | `solver.py` imports `validator.py`: every schedule `find_schedules` produces is passed through the schedule checker, compared with the pins, and checked for the right number of breaks and for repeats. A failure raises an error (it is a bug, and is never returned). The dependency rule becomes `models <- io, conflicts, selection, report <- validator <- solver <- cli`. OR-Tools is imported only when a search runs, so `solver.py` can always be imported and the pre-checks work without it; if it is missing, `SolverNotInstalled` gives the install command. | Gives the guarantee ("the two tools agree") to every caller, command line or UI, instead of relying on each to remember. Keeps the schedule checker installable without OR-Tools. |
| D40 | 2026-10-17 | `find_schedules` returns a `FinderResult`: a status (found / exhausted / stopped), the schedules, a plain-language explanation, and the positions of blocking pins. Pre-check failures, including pins that do not fit the show (outside the slots, unknown name, too many pinned breaks), are returned as *exhausted* with an explanation, not raised. All failures are reported together and no search is run. The wording lives in `solver.py`, as the checker's structural-problem wording lives in `validator.py`; both interfaces use the same result, so the aim of D26 (identical wording) is kept. `count` is how many schedules to list (ask for one extra to learn whether more exist); the time limit is a parameter (default 30 s, Q13). | Only three statuses. A pin naming a performance that does not exist means no schedule can satisfy the request, and the organiser needs the reason. Programming mistakes (negative gap, count below 1) raise `ValueError`. |
| D41 | 2026-10-17 | `pyproject.toml` asks for `ortools>=9.15,<10`. It has been tested only with 9.15.6755. | The code uses the current method names (such as `new_int_var`), and the order of the list can change between versions (D32). |
| D42 | 2026-10-19 | Exit codes of `schedule-finder`: **0** at least one schedule was written; **1** none written (none exist, the time limit was reached first, or none of the numbers picked exist); **2** the command or input files could not be used, or the output file already exists. | Same idea as the checker (D27): a script can tell "no result" from "could not run". |
| D43 | 2026-10-19 | Output files are named `schedules[_seed{S}]_{pick}.csv`: `schedules_1-5.csv`, `schedules_seed42_6-10.csv`, `schedules_1_4_9.csv`, `schedules_all.csv`. A very long pick is shortened to its first and last number. The output folder (default `output`) is created if missing. An existing file is **never overwritten**: it is refused with a message before the search starts, and the file is also opened in exclusive mode as a second guard. (Q15) | Each batch gets its own file, so the printed next-batch command cannot overwrite the previous batch, and the name shows which numbers a file holds. |
| D44 | 2026-10-19 | The next-batch command is printed only when more schedules exist. The next batch is the same size as this one and starts after the highest number written (with `all`: the next `limit` schedules). It repeats every setting that matters and leaves out the ones at their default, so it can be pasted and run. To know whether more exist, a run asks the finder for one extra schedule (D33). | Nothing has to be worked out by hand (D17). |
| D45 | 2026-10-19 | `--time-limit SECONDS` is a command option, default 30. One search may take at most that long; reaching it is reported as "stopped", never as "none exist". (Q13, settled as proposed) | 30 s is far above the slowest answer in the experiment (1.73 s) and still bounded. To change the default, change `DEFAULT_TIME_LIMIT` in `solver.py`. |
| D46 | 2026-10-19 | Choosing schedules from the finder's list (`schedules_to_request`, `apply_selection`, `Picked`) lives in `selection.py`. The wording of the finder's messages lives in `report.py` and takes plain values, because the two files sit side by side and may not import each other. `cli.py` only calls them and prints. | The UI reuses the same rules and wording (D17, D26). |
| D47 | 2026-10-19 | `schedule-finder` reads and checks everything it can before searching (performer file, fixed-positions file, the pick, whether the output file exists) and reports every problem in one go. It also stops at once, with the install command, if OR-Tools is missing, even for a request the pre-checks alone could have explained. | A typo in `--pick` should not cost a long search, and one message is better than several runs. |
| D48 | 2026-10-26 | The UI is a thin Streamlit page. `src/performance_scheduling/app.py` is the only file that imports Streamlit. It imports only the shared layer (`models`, `io`, `selection`, `report`, `validator`, `solver`) and never `cli`. It holds no scheduling logic and no sentences beyond labels and headings. `tests/test_app.py` checks the import rules. (Proposed in `ui-design.md`; built as written in task U2. This row was missing from the log.) | The command line and the page must not be able to disagree (D26, D46), and the core stays separate from the UI (D8). |
| D49 | 2026-10-26 | The page runs on the user's own computer, keeps data in memory for the session, sends no usage statistics (`gatherUsageStats = false` in `.streamlit/config.toml`), writes nothing to disk except a file the organiser downloads, and never uses on-disk caching. It must not be hosted publicly with real data. (Proposed in `ui-design.md` section 8; built as written in task U2. This row was missing from the log.) | Performer names are personal data (`repo-structure.md`, data folder policy). |
| D50 | 2026-10-24 | Table helpers (task U1): `io.schedule_rows` and `report.overview_rows` return a table as rows of text with the **heading row first**. `format_schedules` writes those rows as CSV and `format_overview` lines them up as text, so the page and the command cannot differ. The refusals for bad schedules (none, different lengths, a name that cannot head a column) moved into `schedule_rows` with the same messages. In the overview, "Problems" still counts structural problems if there are any, otherwise pairs of performances (not individual violations). | The page shows the same rows as the command (D26, D46). One rule for the heading row lets the page take row 1 onward as data and row 0 as the column names. |
| D51 | 2026-10-24 | Uploads (task U1): `io.decode_text(raw, name)` is the one place bytes become text: UTF-8, a leading byte-order mark accepted, line endings untouched, and the same "CSV UTF-8" message naming the file. `read_text` reads the bytes and calls it. `io.performer_file_columns(text)` lists the header names for the column pickers using the loader's separator detection and header tidying (shared `_header_names`: names tidied, empty trailing columns dropped, empty middle columns kept). It returns an empty list when there is no usable header and leaves the explanation to the loader. | An upload arrives as bytes, not a path. A name offered in a picker must be one the loader accepts (D26). |
| D52 | 2026-10-24 | Sentences and the next batch (task U1): `report.format_found(count, numbers)` writes "Found 5 schedules (numbers 1-5)." and refuses a count below 1 (the no-schedule box is shown instead). `report.no_schedules_heading(status)` reads EXHAUSTED as "No schedule exists." and any other status as the time limit, as before. `selection.next_pick(selection, limit, last_number)` holds the next-batch rule (D44) and returns only the pick text; `cli.py` reads the batch size back from that text with `parse_selection`, so the rule exists once. | The command and the page share one rule and one wording (D26, D46). If the page needs the batch size on its own, add a small `batch_size` helper then. |
| D53 | 2026-10-26 | App skeleton (task U2, with Q16 answered as (a): only the project owner uses the page, built so the folder can be given to others later). (1) The page runs on one computer and `.streamlit/config.toml` sets `server.address = "localhost"`, so only that computer can open it. Giving the folder to someone else means they run it on their own computer; the config and the example file travel with the folder, and nothing in the page depends on a path outside it. Hosting or sharing over a network stays out of scope and needs `data-privacy.md` first. (2) The same file also turns off usage statistics, hides tracebacks (`showErrorDetails = "none"`), hides the Deploy button (`toolbarMode = "minimal"`) and limits uploads to 5 MB. Streamlit reads the file from the folder it is started in, so the launcher in U5 must start from the project folder. (3) A file with a different name or different contents, or removing the file, clears every result, pin, setting and column choice. The column pickers then ask again even if the new file has the same headers; the page never guesses. (4) Warnings and error boxes use `format_issues`, so they carry the command's wording, its "WARNING:" and "ERROR:" labels and its cut-off of 20 with "... and N more" for warnings; errors are always listed in full. Names are escaped so that `*`, `_`, `$` and `[` show as typed. (5) Anything unexpected while reading the file gives one short message with no names and no traceback (the *proposed* item in `ui-design.md` section 4.6, now built for the performer file only). (6) The tabs are placeholders until U3 and U4 fill them, and stay hidden until a file has loaded without errors. (7) One session key beyond the six in `ui-design.md` section 4.5: `upload_round`, which gives the upload box a new identity so "Clear all data" also empties it in the browser. (8) The status line ("name: 12 performers, 6 performances") is built in `app.py`, not `report.py`, because U2 does not touch `report.py`; it is a count, not a rule. Move it into `report.py` if you want the principle kept to the letter. | Q16 (a) is the simplest and safest answer for personal data. The checks are in `tests/test_app.py`. |
| D54 | 2026-10-26 | Pins are entered with a guided form, not an editable table (Q17, answered). The item is chosen from the show's performances plus "Break", and the slot is a number from 1 to the number of slots, so a typo cannot happen. Built in task U4; U2 only keeps the `pins` key ready. | `AppTest` cannot drive `st.data_editor`, so a table could not be tested (`ui-design.md` sections 3 and 4.3). |
| D55 | 2026-10-31 | "Check a schedule" tab (task U3). (1) The result is worked out again on every run from the three things on the page (performer file, schedule file, rest), so it can never be out of date and nothing is kept in `st.session_state` for it (no new key; `run`, `pins` and `form` stay for U4). The rest is a number box (`check_gap`, default 1, minimum 0 like `--gap`) with the same label as the finder's; the command's sentence explaining the gap is not repeated on the page. The command's `--schedule-column` is not offered: the organiser sees every column. (2) Sentences come from the shared layer: the verdict, slot count and tightest-spacing lines from `format_check` (read by line position: line 0 verdict, line 1 slots, line 4 "Spacing was not checked.", last line tightest spacing; the tests fail if that layout changes), the overview from `overview_rows`, the closing sentence from `format_totals`, the download from `format_violations_csv`. (3) The overview and the pairs are plain-text tables (`st.dataframe`), so a name cannot turn into bold, a link or maths. The pairs table has one row per pair: No., first performance and slot, second performance and slot, slots between, slots needed, performers affected (a count). (4) "Who is affected" is an expander listing the performers for each pair, the command's second list. It is open when one schedule is checked and closed when several are, so the names are at once visible in the common case without burying a long page. Names there are escaped like the rest of the page. (5) Problems with the schedule itself (missing, unknown or repeated performances) get their own red box with "Spacing was not checked." and the finder's "Did you mean" hints; no pairs table, no download and no tightest-spacing line are shown for that schedule. (6) Each schedule's heading carries an icon and the word VALID or INVALID. With several schedules the closing sentence is green when all are valid, yellow when some are invalid and red when all are. (7) With more than 10 schedules valid ones appear only in the overview (D28). The number 10 (`FULL_DETAIL_UP_TO`) and the sentence "Valid schedules are listed in the table only." are copied from `cli.py` into `app.py`, because the page may not import `cli` (D48) and U3 does not touch `report.py`. Move both into `report.py` if you want the principle kept to the letter, as with D53 (8). (8) "Download the problems (CSV)" appears only when there is at least one violation, is named `<schedule file name>_problems.csv`, and is UTF-8 with a byte-order mark, like every CSV the command writes (`io.write_text`), so Excel shows accents correctly. (9) A schedule file that cannot be used gets a red box that names the file, and the performer file stays loaded. Warnings about the schedule file are shown in full in an open expander headed "... to check in the schedule file", so they are not confused with the performer file's; the performer file's warnings are not repeated, because they are already shown above the tabs. (10) Anything unexpected while reading the schedule file, or while checking, gives one short message with no names and no traceback (D53 (5) extended). (11) The schedule upload box takes its key from `upload_round`, like the performer box, so "Clear all data" empties it in the browser too. A new performer file keeps the schedule file and checks it again; a performer file that cannot be used hides the tabs, which also drops the schedule file and the rest. | Keeps the page thin (D26, D46, D48) and the result in step with what is on screen (`ui-design.md` principle 6). The checks are in `tests/test_app.py`; twelve deliberate breaks of the code were each caught. |
